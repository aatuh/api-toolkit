# Migrating to v5

V5 is not published. Do not change application imports, module requirements, or
production release claims to v5 until a verified v5 release and migration note
exist. Current supported consumers use the v4 core and optional contrib module
paths described in [the v4 migration guide](v4.md).

The planned v5 module boundaries are an architectural proposal, not a current
compatibility promise. Review [ADR 0002](../adr/0002-v5-module-decomposition.md)
and [the focused v5 core surface](../v5-core-surface.md) before evaluating a
future move. Generated services remain application-owned: regenerate a fresh
project with a published CLI, compare it with the application, and migrate
application changes deliberately. Do not assume an in-place upgrade.

When v5 is released, this guide will name the exact source module, supported Go
and platform matrix, compatibility baseline, removals, replacements, and
rollback procedure. Until then, use the v4 current-release policy in
`VERSIONING.md`, `docs/support-policy.md`, and `SECURITY.md`.
