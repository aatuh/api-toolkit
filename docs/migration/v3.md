# V3 Migration Guide

Audience: application teams upgrading api-toolkit dependencies or generated
services to the v3 line.

This guide is the human upgrade path. `VERSIONING.md` remains the compatibility
policy, and `docs/release-notes.md` remains the dated change log.

## Before You Upgrade

1. Confirm the target version. The latest published release line documented in
   this repository is `v3.1.2` for the root module and `contrib/v3.1.2` for
   contrib.
2. Confirm your toolchain. Root and contrib target Go 1.25.x; local checks
   should run with `GOTOOLCHAIN=local`.
3. Identify which adoption path you use:
   - root-only library packages from `github.com/aatuh/api-toolkit/v3`,
   - contrib adapters from `github.com/aatuh/api-toolkit/contrib/v3`,
   - app-owned generated service code from the contrib CLI.
4. Read the package rows in `docs/api-reference.md` and
   `docs/core-readiness.md` for packages you standardize on.

## Root Library Upgrade

```sh
go get github.com/aatuh/api-toolkit/v3@v3.1.2
go mod tidy
go test ./...
```

If your service has local docs or contract gates, run the nearest equivalent of:

```sh
GOTOOLCHAIN=local make docs-check
```

Review:

- `VERSIONING.md` for stable API and compatibility-only package status.
- `docs/api-inventory.md` for exported symbol inventory.
- `docs/deprecations.md` for replacement paths and removal horizons.
- `docs/release-notes.md` for behavior, security, dependency, and generated
  scaffold changes.

## Contrib Adapter Upgrade

```sh
go get github.com/aatuh/api-toolkit/contrib/v3@v3.1.2
go mod tidy
go test ./...
```

Contrib packages are outside the stable core API promise. Before upgrading,
check:

- `docs/package-classification.tsv` for `supported-adapter`,
  `experimental`, `wrapper-only`, `tooling`, or `generated` status.
- `docs/supported-adapter-contracts.tsv` for supported-adapter behavior
  evidence.
- `docs/contrib-api-drift-packages.txt` and release notes for drift review.

## Generated Service Upgrade

Generated services are app-owned generated code. Do not blindly regenerate over
local product changes.

1. Generate into a temporary directory with the new CLI version.
2. Diff generated infrastructure files against your service.
3. Port intentional scaffold changes manually.
4. Re-run service tests, OpenAPI checks, contract lint/diff, and any Docker
   integration checks you own.
5. Keep product code, provider workflows, and operational settings in the
   generated app repository, not in the toolkit root module.

Use `docs/scaffold-first.md`, `docs/full-service-scaffold.md`, and
`docs/reference-service.md` for scaffold-specific expectations.

## Common V3 Migration Notes

| Area | Migration note |
| --- | --- |
| Module paths | Root imports use `github.com/aatuh/api-toolkit/v3`; contrib imports use `github.com/aatuh/api-toolkit/contrib/v3`. |
| Stable vs compatibility-only | Compatibility-only packages remain protected for v3 but should not guide new generic designs. |
| `ports` | New abstractions should usually be app-owned or package-local. Do not expand root `ports` without the design evidence in `docs/stable-core.md`. |
| Billing compatibility | Use `github.com/aatuh/api-toolkit/v3/compat/billing` for v3 hosted-checkout compatibility surfaces. |
| Health/admin endpoints | Prefer public liveness/readiness and admin-only detailed health, metrics, and pprof. |
| Rate limiting | Prefer `middleware/ratelimit.Limiter` for app and adapter contracts; it is a v3 source-compatible shim over `ports.RateLimiter` before v4 shrinks broad root ports. |
| Timeouts | Hard-timeout buffering is for finite responses only; streaming, SSE, websocket, and large-download routes need opt-outs. |
| Idempotency | Multi-instance or production services should use durable storage, tenant-scoped keys, and explicit unsafe-write route policy. |
| OpenAPI validation | Request validation can run broadly when contracts are complete; response validation should be route-filtered for finite responses. |

## Verification Checklist

- [ ] `go test ./...` passes in the application module.
- [ ] `go mod tidy` produces an intentional diff.
- [ ] Import paths use `/v3` for root and `/contrib/v3` for contrib.
- [ ] Package tier changes are understood from `docs/package-classification.tsv`.
- [ ] Deprecations and compatibility-only packages are reviewed.
- [ ] Streaming and large-response routes avoid response buffering.
- [ ] Generated service diffs are reviewed as app-owned code.
- [ ] Release notes for every skipped version are read before production rollout.
